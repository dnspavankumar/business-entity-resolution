# Approaches tried and lessons learnt

This file records what we tried, what worked, what failed, and why. It is meant for a new chat or AI assistant.
**Read it before proposing ideas:** most of the obvious ideas below were already tried.
(Scores: LB = public leaderboard. "Local" = the US+India harness in `evaluation/evaluate.py`.)

## 2. Key facts about the data (all verified on train labels)
- **Decoys exist and are generated by rules** (the "decoy fingerprint"):
  - The house number is the Source-1 number **+ offset**, with offset in {1,2,3,4,5,7,9,11,13,21}. The offset is almost always positive (99.8%), and all decoys of one entity share one offset (97.8%).
  - The name usually changes too: a legal-form swap (inc → corp, llc → ltd) or an added or substituted word (Holdings, Group, Industries; France: Développement, France, "& Fils").
  - Other decoy types: same address with the first word replaced (US: a person's name; India/France: the business-type word, e.g. "Dunkerque Club EURL → Dunkerque Collège EURL"), and the same name at another location.
- **The test has about 3× more decoys per entity than train** (US ×3.00, India ×3.04, measured from candidate counts).
- **True-match noise is symmetric:** a true record is +k from its Source-1 number as often as −k. Decoys are only +k.
- **Empty-address records** (3–4%) whose name is shared by several Source-1 entities ("twins") are **coin flips**. Among exact same-name twins, the owner is independent of:
  - file order (50.2%) and ID number (49.9%);
  - address properties (AUC 0.53);
  - the other twin's records, entity size, a Bayesian count prior, the Source-2/3 split, and spelling.

  Local loss: EA raw-twin 0.0045, core-twin 0.0011, unique 0.0009.
- **No leaks:** row order, IDs and twin order are random.
- **France** (no labels): names follow "place + business type + legal form", so 26.8% of French entities have a same-name twin in the same city (US 1.1%). France has far fewer ±1/±2 true typos than the US.
- **Test decoy groups:** in the test, a decoy entity often has 2+ records at the same shifted number (19% of US strong-offset pairs, vs 1.2% of train decoys). This breaks features like "another record agrees with me".

## 3. Lessons (most important first)

**L1. Validation from train lies unless it copies the test decoy density.**
v1 scored 0.9855 locally but 0.973 on the LB, because the test has about 3× more decoys. The fix is `src/local_eval.py`: every wrong pair whose record matches nothing counts ×3.0 (US) or ×3.04 (India), plus the same prior shift and per-entity selection as the submission. Since then local and LB agree within about 0.0004.

**L2. Model the adversary, not generic noise.**
The gains came from decoy-specific features: signed house-number difference, offset membership, legal-form swap direction, added-word vocabulary scores, and cluster context. We also trained with negatives ×2.6 and shifted the prior per country.

**L3. Choose matches per entity by expected F0.5, not with a global threshold.**
The empty set is one of the options, so singletons are handled. Loosening thresholds (v3) always hurt.

**L4. For France, use label-free checks.**
- The **count profile** tells true noise (it grows with entity size, and singletons have almost none) from decoys (flat profile).
- It predicted the France fix gain (+0.0050), and the LB gave +0.0049.
- **But it is biased** when the change depends on the model score or cluster context (pairs added by K×1.5 were 86% true on labelled US data, while the profile said 40%). It is also biased for dominant classes. Use it only for rule-based classes.

**L5. A local gain can be a test loss when train and test differ.**
- Sibling-agreement features ("another record of the entity from the same source has the same deviation") gave +0.0004 locally.
- The test **symmetry check** (`evaluation/sym_check.py`: accepted +k minus −k) showed extra upward-offset decoys accepted, because of the test decoy groups.
- We dropped those features and **capped** upward-offset pairs at the v10 score.
- Always run the symmetry check before uploading a matcher change.

**L6. The new matcher is not used for France.**
v15's matcher added 1,261 France empty-address pairs, 42% of them to entities with a same-name French twin (coin flips). France therefore keeps the v13 decisions (`merge_countries.py`).

**L7. More training data helps, but slowly.**
Learning curve (training fold size → local score): 0.16M 0.98684, 0.3M 0.98728, 1.1M 0.98774, 1.9M 0.98787, 2.9M 0.98802. Doubling now gives about +0.0001.

**L8. Don't fight the irreducible part.**
Many ideas for the empty-address twins failed:
- entity-size prior, Bayesian counts, Source-2/3 split;
- spelling copy, twin-compatibility features, name-signature groups;
- a pseudo-name character model (AUC 0.68).

**L9. Uploads are precious.** Test locally, upload only clear wins, and keep the last upload a good file (the private LB decides).

**L10. The symmetry check needs a local reference when the change is score-driven.**
K×1.5 adds pairs that are asymmetric on the test (US: 408 at +1/+2 vs 27 at −1/−2). Locally, the pairs K×1.5 adds show the same asymmetry (48 vs 2), and those +1/+2 pairs are **92% true**. The model pushes true +1/+2 typos toward the borderline, because decoys also use +1/+2, so lowering the bar adds them first. Always compare the test pattern with the same analysis on labelled local data before calling it decoys.

**L11. candidate_pairs.tsv counts for the final ranking** (organizer update on 2026-09-27): smaller per Source-1 entity is better, and the blocking must scale.
- Ours: 3.98 per S1, with 97.7% local recall.
- We did not shrink it further with the stage-2 score (p2 < 0.001 → 3.74 per S1). That would be cosmetic and would make the candidates look like the matches.

**L12. A text model that reads both records together adds what hand-made features miss.**
- The LightGBM matcher had hit a plateau: doubling the data gave only +0.0001.
- A fine-tuned cross-encoder (AUC 0.946 on the uncertain pairs, vs 0.979 for p2) is weaker alone, but its errors differ from p2's. Stacked, the AUC rose to 0.988 and the local score by +0.0014, mostly through fewer false positives (US 325 → 190).
- It needed a GPU. Free Colab T4 was enough: 646K training pairs, 2 epochs, about 35 minutes. Only the uncertain pairs (about 1.1M test pairs) are re-scored.

**L13. Models trained on US/India do not transfer to France's decisions.**
- This happened for the v15 matcher (L6) and again for the cross-encoder (v18).
- France accepted pairs with a very low cross-encoder score still have a true-match profile. They are French-specific true noise (suffixes like "France" / "Services"), which the US/India-trained text model finds odd.
- Keep France on its label-free-validated rules.

**L14. A second cross-encoder of similar size adds little.**
- XLM-R base alone scored 0.98952, the same as DistilBERT's 0.98955. Together they reach 0.98969 (+0.00014).
- More gain would need a different signal, not another model of the same kind.
- The remaining loss is about 60% empty-address same-name twins, which text cannot resolve.

**L16. The last push for 0.99 (evening of the deadline day), all label-free on the test:**
- **IDs:** no leak. For true pairs, S1-id mod m equals record-id mod m at chance rate for m = 2…1000, and the correlation is 0.
- **Per-source counts:** each S1 has 0–5 Source-2 and 0–6 Source-3 records, a broad spread with no hard cap to exploit.
- **India offsets:** the test accepts about 2,750 more +1/+2 offset pairs than the local true-pair reference predicts, which are likely decoys. They are spread over cells (band × S1-number-confirmed × shared-offset × name change) with decoy shares of 0.1–0.3. Removing a pair pays only above a decoy share of about 0.3, so there is nothing safe to remove.
- **France −k offsets:** France accepts only 60% of its −1/−2 pairs (US 97%), but that is just 338 pairs, a negligible gain.
- **Research:** a web research agent found no public write-ups with top-solution tricks. The literature ideas (calibration, entity-level empty-set model, seed averaging) are each worth about +0.0001.
- **Reading of the top scores (about 0.9915):** they most likely come from much stronger text models on the resolvable pairs, not from the empty-address twins. That would need large cross-encoders trained on millions of pairs and scoring every candidate (re-ranking, not only the best pair). That is days of GPU work.

**L17. The deep analysis is in `DEEP_ANALYSIS.md`.** It has the loss per bucket, the kinds of misses (pseudo-names, shared names, web domains, native script), coin-flip rates per country, and the ranked future-work list.

**L18. Engineering lessons:**
- The cloud box has 2 CPUs and about 6 GB usable RAM, so work in chunks.
- Predict one country per process, cast to Float32, and fill LightGBM matrices column-group-wise from parquet (`stage2_v14.fit`).
- `stage2_v14.py predict` **skips countries whose `test_best_v14_<c>.parquet` already exists**. Move old files away before predicting with a new model.
- The link to the user's PC drops sometimes. Move big files in chunks and check MD5.
- Polars: watch for duplicate column names (`list(dict.fromkeys(...))`) and u32 underflow (cast to Int64).

## 4. Tried and dropped (≤ +0.0001 locally, or unsafe on the test)
- Larger LightGBM or more trees, 3-seed averaging, blending with the older model.
- Pattern features, per-country prior values, "unreachable-aware" EV selection (`ev_select_u`), isotonic recalibration.
- Separate K scaling for empty-address vs other pairs (tiny gain).
- A LightGBM stacker for ONE cross-encoder with extra pair features: +0.00008. With both cross-encoders plus K×1.75 it reached +0.00012, which became v20.
- Twin-compatibility counts, pseudo-name character model, name-signature groups.
- Sibling-agreement features (L5).
- A class-level France profile scan suggested France was under-accepting. Local checks showed the method is biased there, and samples of the rejected France pairs looked like decoys, so no change was made.

## 5. Where the remaining loss is (local US+India, v14/v15)
| cause | loss | can we fix it? |
|---|---|---|
| empty-address records with same-name twins | ≈ 0.0045 | no signal found (L8) |
| records with an address but twins / partial address (India) | ≈ 0.0025 | partly: a better text model, the rescue search |
| false positives (decoys accepted) | ≈ 0.0017 | a better text model? |
| true pairs rejected (with address) | ≈ 0.0016 | a better text model? |

The top teams are at about 0.9915, about 0.0045 above us. That gap is about the size of our "irreducible" empty-address twin loss. So either they found a signal for those twins that we missed, or they are better at the text-matching buckets. Such a signal would have to use something beyond order, IDs, sizes and sources, which were all tested. **This is the main open question.** The GPU cross-encoder (`gpu_crossencoder/`) targets the text-matching buckets.
